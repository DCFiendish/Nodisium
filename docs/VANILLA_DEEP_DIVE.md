## Part 4 — New findings from the previously-unaudited files (2026-09-12)

> **Fixed same day.** Both HIGH items and both MEDIUM items below are fixed: `Shelves` now
> restores handlers on `InstanceChunkLoadEvent` (once per chunk load) instead of
> `PlayerChunkLoadEvent` (once per player view); `Signs.sessions`/`Vanish.vanished` are now
> `ConcurrentHashMap`; `PlayerData.saveAll`'s periodic autosave now runs on its own dedicated
> executor instead of Minestom's shared scheduler pool; `Storage.saveAll` now returns a
> `CompletableFuture` and the periodic task fires-and-forgets it instead of blocking on `.join()`
> (`stop()` still joins, since shutdown must wait for the final save); `MovementAntiCheatListener`
> now scales its per-move distance allowance by real elapsed time between moves, and rate-limits
> its violation logging to once per 5s per player. The two remaining LOW items (the global
> `Commands` inventory-sync lock, and the small bounded O(n) refreshes in `Koth`/`Vanish`) were
> left as-is -- they're accepted trade-offs at current scale, not bugs.

### HIGH

- **`Shelves.kt`'s legacy-restore scan runs a full chunk-height block scan on every single `PlayerChunkLoadEvent`, for every player, forever — not once per chunk load.** `managers/Shelves.kt::onPlayerChunkLoad` → `restoreChunk`. `PlayerChunkLoadEvent` fires per-player, every time that chunk enters that player's view distance (walking, teleporting, respawning, reconnecting) — it is not deduplicated per chunk-lifetime. Every single firing does a triple-nested loop over the chunk's *entire* height range (`chunk.minSection*16..<chunk.maxSection*16`, i.e. up to ~384 Y-levels on a standard Overworld dimension type) × 16 × 16 = up to ~98,000 synchronous `getBlock()` calls while holding `chunk.lockReadLock()`, just to find any `_shelf` blocks so their handler can be rebound. Contrast `ItemFrames.kt`, which solves the identical "handler not preserved across chunk unload" problem with `InstanceChunkLoadEvent` (fires once per chunk load, not per viewer) plus a persisted `frameAnchorsIndexedTag` so the expensive full scan only ever runs once per chunk, ever. `Shelves` has neither optimization: no per-viewer dedup, no indexed/cached flag, so the same chunk gets rescanned in full for every player who ever looks at it. At 200-player scale with players moving through the world (the project's own stated target), this is repeated, unbounded, synchronous full-chunk-height work directly on the hot chunk-load path — a strong candidate for real TPS impact, and it gets worse linearly with player count and world traversal, not something that only shows up under attack/edge-case load.
  - Fix shape: switch to `InstanceChunkLoadEvent` (once per chunk, not per viewer) and add the same kind of indexed/persisted-tag shortcut `ItemFrames` already uses, so the full block scan only ever runs once per chunk's lifetime.

- **`Signs.sessions` and `Vanish.vanished` are still plain (non-thread-safe) `HashMap`s/`mutableMapOf` mutated from concurrent per-player event handlers — the exact bug class fixed everywhere else in this same pass.** Per the project-wide policy in [`research-todo/01-concurrency-model.md`](research-todo/01-concurrency-model.md) (confirmed against Minestom's own source: event handlers are only synchronized per-entity/chunk, never for shared global state), any collection reachable from more than one player's event handlers needs to be a thread-safe collection. Today's session converted exactly this bug class to `ConcurrentHashMap`/`ConcurrentHashMap.newKeySet()` in `Commands.lastLocation`/`ignored`, `Elevator.columns`, `Recipes.workspaces`, `Mannequin.inventories`/`corpses`, and `Blocks.stonecutters` — but `Signs.kt` (`private val sessions = mutableMapOf<Player, EditSession>()`, written from `onEdit`/`openEditor`/the `PlayerDisconnectEvent` handler) and `Vanish.kt` (`private val vanished = mutableMapOf<UUID, State>()`, written from `onInput`/`vanish`/`unvanish`/`onSpawn`/`onDisconnect`) postdate that pass and never got it. Two different players opening a sign editor, or vanishing/unvanishing, at the same instant on two different chunk-tick threads race a plain `HashMap.put`/`remove` on the same shared map instance — the classic concurrent-structural-modification corruption/infinite-loop hazard, on a player-facing UI path (sign text silently not saving/applying to the wrong session) and a staff-tool path (vanish state leaking or failing to toggle) respectively.
  - Fix shape: `ConcurrentHashMap` for both, same pattern as the five call sites already fixed today.

### MEDIUM

- **The two autosave tasks added earlier in this same pass (`PlayerData.saveAll`, `Storage.saveAll`) run their work directly on Minestom's shared global scheduler thread pool, not offloaded to their own executor.** Per `research-todo/01-concurrency-model.md`, `MinecraftServer.getSchedulerManager()` is a shared pool used by *every* periodic system in this module (`Crops`, `Saplings`, `Food`, `EnvironmentalDamage`, `Combat`, `Koth`). `PlayerData.saveAll()` synchronously performs real blocking disk I/O (gzip-compress + write + atomic rename) for every tracked online player, one after another, on whichever pool thread runs the task — no offload to an async/IO executor. `Storage.saveAll()` similarly blocks the pool thread on two sequential `CompletableFuture.allOf(...).join()` calls, waiting for every barrel's deferred write and then every touched chunk's disk save to complete. Neither is wrong in isolation (both are correctness fixes over the previous no-autosave/blocking-event-thread state), but both now tie up a shared pool thread for a duration that scales with player count / barrel count, once every 300 seconds — worth confirming the scheduler pool has enough worker threads that a 200-player save sweep doesn't starve `Crops`/`Food`/`EnvironmentalDamage`/`Combat`/`Koth`'s own scheduled ticks for the duration, given this project's stated TPS priority. If it does starve them, the fix shape is running the actual I/O on a dedicated executor (e.g. `CompletableFuture.runAsync` with its own thread pool) and only touching Minestom state via `scheduleNextTick` for the parts that require it.

- **`MovementAntiCheatListener`'s speed/fly-hack thresholds are fixed per-move-event distance caps, not normalized to elapsed real time between moves.** `listeners/MovementAntiCheatListener.kt::onMove`. The horizontal-distance and unsupported-ascent checks compare raw position deltas between consecutive `PlayerMoveEvent`s with no time component — under a TPS drop or any scheduling delay that lengthens the real-world gap between processed move events, a legitimately-walking player covers more real distance per event and can trip the cap, triggering a false-positive snap-back (`event.isCancelled = true`). This is exactly the scenario most likely during a genuine lag spike, so the anti-cheat's failure mode actively compounds server lag into visible player-facing rubber-banding rather than degrading gracefully. Also note: each violation does a synchronous `println` (see LOW below).

### LOW

- **Every violation branch across `MovementAntiCheatListener`, `Koth`/`Elevator`/others logs via bare `println`/`System.err.println` on the hot event-dispatch path**, not a buffered/async logger. `System.out`/`System.err` are backed by a single synchronized `PrintStream`; under many concurrent per-chunk event-dispatch threads (Minestom's normal operating mode), a burst of anti-cheat violations (a single misbehaving or malicious client spamming movement) serializes every one of those threads on that one lock plus console I/O. Low severity in isolation, but worth batching/rate-limiting or moving to an async logger if anti-cheat false-positive rates ever get non-trivial at 200-player scale.
- **`Commands.synchronizeInventoryChange` takes one global `synchronized(viewingLock)` lock on every `InventoryItemChangeEvent` server-wide** (every chest, crafting grid, ender chest, hopper-fed container — not just `/invsee` sessions), since the listener is registered on `Vanilla.eventNode` unscoped. Correct and necessary for the `/invsee` mirroring it protects, and the critical section is cheap today (the `viewing` map is normally empty), but it is a single global contention point sitting on literally every inventory-slot-change event on the entire server. Not an issue at current scale; worth remembering if inventory-click volume or concurrent `/invsee` usage grows.
- **`KothListener.onMove` triggers a full `Koth.updateBossBars` refresh (all active KOTHs × all online players) synchronously from `PlayerMoveEvent` whenever any player's capture state flips**, in addition to the once-a-second scheduled refresh. Bounded by how often players cross a KOTH zone boundary — not a concern at the current handful-of-KOTHs scale, but scales as O(active KOTHs × online players) per capture-state change.
- **`Vanish.onSpawn` unconditionally calls `refreshVisibility()`, which is O(vanished + spectator players), on every single player join** — bounded and cheap unless the vanished/spectator count is large, but noted since spawn events happen constantly (every reconnect burst after a restart).

`vanilla` reimplements baseline Minecraft mechanics on top of Minestom (which ships none): fall/fire/drowning/starvation damage, food/hunger, block-break drop tables, crop/sapling growth, tree-felling, elevators, a kill-reward shop, jukeboxes, barrel storage, player-corpse handling, whitelist, and player-data persistence — plus the command surface for all of it. Its `Combat.kt` is **not** a damage pipeline; it's purely a PvP combat-tag/anti-combat-log system. Real damage sources are `EnvironmentalDamage.kt`, `Food.kt`, and `FallDamageListener.kt`, which flow through the same shared `EntityDamageEvent`/health-attribute system the sibling `combat` library's `applyDamage` also uses.

## Part 1 — How it actually works, by subsystem

### 1.1 Combat-tag / anti-combat-log (`managers/Combat.kt`)

Tracks `expiresAt: ConcurrentHashMap<UUID, Long>` and `bossBars: ConcurrentHashMap<UUID, BossBar>` — correctly thread-safe. Tags a player on taking PvP damage, shows a countdown boss bar, and (per [RESEARCH.md §12](RESEARCH.md)'s design decision) disconnecting while tagged is treated as an instant kill with loot dropped at the disconnect location. `tick()` does an O(n) linear scan of all online players per tagged player every second rather than an O(1) lookup — a low-severity scaling concern, not a correctness bug.

### 1.2 Fall damage (`listeners/FallDamageListener.kt`)

Tracks peak airborne height per player: `fallStartY: ConcurrentHashMap<UUID, Double>`, updated via `merge(uuid, newY, ::maxOf)`. Thread-safe container, but the height is only ever reset on landing, entering water, entering creative/spectator, or entering a vehicle — **never on teleport**. See Part 2 (HIGH) for the consequence.

### 1.3 Environmental damage & food (`managers/EnvironmentalDamage.kt`, `managers/Food.kt`)

Fire/drowning/starvation damage, correctly checks relevant potion effects (Fire Resistance, Water Breathing, etc.) before applying damage — contrasted favorably against `FallDamageListener`'s more limited handling (no Slow Falling/Feather Falling/elytra checks, see Part 2). Both use `ConcurrentHashMap`-backed per-player tick state and a scheduled tick task; correctly thread-safe containers, though see Part 2 (MEDIUM) for the general "global scheduler thread mutates per-instance state" pattern this and several other managers share.

### 1.4 Block breaking & drop tables (`listeners/PlayerBreakListener.kt`, `managers/Blocks.kt`, `listeners/BlocksListener.kt`)

Drop tables live in `VanillaConfig.blockDrops`. **Major correctness gap, not just "no probability weighting":** almost every real ore→resource conversion is missing — Iron/Gold/Diamond/Emerald/Redstone/Lapis/Coal/Quartz/Copper ore all fall back to `ItemStack.of(material)`, i.e. drop the raw ore *block* itself rather than the correct raw resource (iron nugget/raw iron, redstone dust, lapis lazuli, coal item, etc.). `Blocks.stonecutters: MutableSet<Inventory>` is a plain, non-thread-safe `HashSet` — part of the recurring cross-library thread-safety pattern (see Part 2). Tool durability is **entirely unimplemented** anywhere in the repo: no decrement on use, no Unbreaking enchantment check, no breakage at 0 durability.

`nodes`' hidden-ore mining mechanic ([RESEARCH.md §11](RESEARCH.md)) operates on top of this same block-break path via `Nodes.config.oreBlocks` (e.g. plain STONE) — no custom `BlockHandler` needed, since the "ore" is a drop computed on break, not a distinct block type.

### 1.5 Crops, saplings, tree-felling (`managers/Crops.kt`, `listeners/CropsPlantListener.kt`, `managers/Saplings.kt`, `listeners/SaplingsListener.kt`, `managers/TreeFeller.kt`, `listeners/TreeFellerListener.kt`)

- **Crops**: flat global map scan every tick (`Crops.crops: ConcurrentHashMap<BlockKey, CropsPlantedCrop>`), no per-instance/chunk partitioning, no unloaded-chunk skip — a real scaling concern for large farms at 200-player scale, though not incorrect. `CropsPlantListener` self-validates farmland adjacency; this is the **only** block-placement permission logic anywhere in `vanilla` — general placement protection is entirely `nodes`' responsibility (confirmed, no generic gate exists here).
- **Saplings**: correct `ConcurrentHashMap` container, growth via a repeating scheduled tick that re-verifies the block is still a sapling before growing (self-healing against external removal). Giant (2×2) trees require all four corners to still match at grow time. However, `SaplingsListener.onInteract`'s bone-meal counter uses Kotlin's `getOrPut` on this `ConcurrentHashMap` — see Part 2 (MEDIUM/HIGH), since `getOrPut` is not itself atomic regardless of the underlying map type.
- **Tree-felling** (credited: ported from `IDev-mc/TreeFeller`): flood-fills connected logs, **capped** by `config.treeFellerMaxSize`/`treeFellerMaxLeaves`/`treeFellerLeafMaxDistance` (returns empty rather than unbounded flood-fill), removes blocks gradually via a rate-limited scheduled task rather than all at once. Well-implemented anti-grief/anti-DoS design — one of the better-engineered subsystems in the repo.

### 1.6 Player data persistence (`managers/PlayerData.kt`, `PlayerDataSerializer.kt`, `PlayerDataDeserializer.kt`)

Real Minecraft-format persistence: one gzip-compressed NBT `.dat` file per player (`BinaryTagIO`), not hand-rolled JSON — notably more "vanilla-correct" than `nodes`' persistence. Saves health, food/saturation, KillShop points, game mode, fly flags, position/orientation, main + ender-chest inventory, cursor item, ignore-list.

- **Loads** only on `PlayerSpawnEvent` where `event.isFirstSpawn` is true — confirmed, no reconciliation happens on later spawns (e.g. instance/dimension changes).
- **Saves** only on two triggers: `PlayerDisconnectEvent`, and a JVM shutdown hook (`Vanilla.kt`) that calls `saveAll()` over every tracked player. **There is no periodic autosave task anywhere in the repo.**
- All I/O is synchronous/blocking, on the calling event-dispatch or shutdown-hook thread — no offloading to an executor.
- No file locking, no temp-file+rename — writes truncate the target path directly.
- Shutdown hook only fires on graceful JVM shutdown; it will **not** run on `kill -9`, OOM-kill, native crash, or hard power loss — see Part 2 (MEDIUM) for the durability gap this creates, and Part 2 (CRITICAL) for a concurrency bug this same design produces during an ordinary graceful restart.

### 1.7 Barrel storage (`managers/Storage.kt`, `listeners/StorageListener.kt`)

The standout well-engineered persistence subsystem: barrel contents are serialized into the **block's own NBT** and ride on Minestom's existing chunk-persistence pipeline (`instance.saveChunkToStorage`), rather than `vanilla` inventing its own save format/scheduler. `barrels`/`inventoryToKey` are correctly `ConcurrentHashMap`. Includes a genuinely thoughtful legacy-format migration path (old per-block sidecar `.dat` files auto-migrated into block NBT on first access, archived with a `.migrated` suffix rather than deleted, covered by a dedicated test). See Part 2 for two real bugs this subsystem still has: a synchronous-I/O stall on first legacy-barrel access, and a critical break-time duplication exploit.

### 1.8 Whitelist (`managers/Whitelist.kt`, `listeners/WhitelistListener.kt`)

Plain Gson JSON list + a separate plain-text `whitelist-enabled.txt` toggle file. `entries: ConcurrentHashMap<String, Entry>`, keyed by **lowercased username, not UUID** — `resolveUuid()` only attaches a UUID if the target happens to be online at add-time; otherwise the entry matches purely by username string, meaning a name change or account swap can bypass an offline-added whitelist entry. Every `add`/`remove`/`toggle` rewrites the whole file synchronously and immediately (no batching, but also no atomic rename).

### 1.9 Configuration (`VanillaConfig.kt`)

**There is no file-based config loading at all.** `VanillaConfig` is a plain Kotlin `data class` with hardcoded defaults for every field (feature toggles, paths, crop/sapling timers, food values, block-drop tables, combat timers, environmental-damage constants, shop catalog, etc.); the host application is expected to construct one in Kotlin code and pass it to `Vanilla.init(config)`. No YAML/JSON/TOML mapping dependency exists in the build. `config` is `lateinit var … private set`, assigned exactly once — **hot-reload is architecturally impossible** as built, and there is **zero validation** (no `require()` guards) on any field, so a negative/zero/NaN value for anything (heal amounts, growth timers, combat duration) silently does whatever the downstream arithmetic implies rather than failing fast at boot.

### 1.10 Kill-reward shop (`managers/KillShop.kt`, `listeners/ShopListener.kt`, `commands/Shop.kt`)

Currency is an integer NBT tag on the player entity (`shop_points`), +1 per PvP kill. Catalog is a static config list (no finite stock concept, only cost + a per-player-per-slot cooldown in `playerCooldowns: ConcurrentHashMap<UUID, ConcurrentHashMap<Int, Long>>`). Purchase flow in `onPreClick`: check cooldown → check balance → grant item → deduct balance. Granting before deducting is actually the safe choice for the "inventory full" case, but the whole sequence is an unguarded check-then-act — see Part 2 (CRITICAL) for the resulting dupe/double-spend. `/shop restock` (admin) only clears cooldowns server-wide; it doesn't touch balances or any actual stock, despite the name.

### 1.11 Player death / corpse (`managers/Mannequin.kt`, `listeners/MannequinListener.kt`)

Not a cosmetic-NPC command — entirely automatic, triggered on `PlayerDeathEvent` when the dying player's inventory isn't empty. Spawns an `EntityCreature(MANNEQUIN)` wearing the dead player's skin, holding a fresh loot inventory pre-filled with their items, launched away from the killer, auto-despawning after `config.mannequinDespawnTime` or instantly once looted empty. `despawn()` correctly force-closes all current inventory viewers before removing the entity — the safe pattern that `Storage.kt`'s barrel-break path (1.7) is missing. No permission gate needed (automatic mechanic) and no rate cap on creation — see Part 2 (LOW).

### 1.12 Elevators (`managers/Elevator.kt`)

Iron-block-column-based, ported/inspired by `ccnet elevators`. Columns are lazily scanned (`y = -64..320`) on first interaction and cached; subsequent iron placements/removals update the cache incrementally **only via player-driven block events**. Movement triggers on jump/shift while standing on iron, teleporting to the next cached iron level within `config.elevatorMaxSearch`, verified only by checking the two blocks *above* the target are air. `columns: HashMap<UUID, HashMap<Long, TreeSet<Int>>>` is a plain, non-thread-safe nested `HashMap` — already-known finding, not re-derived here. New findings in Part 2: the cache goes stale on any non-player-driven block change (explosions, external edits), and it's never pruned per-instance, growing unbounded over long uptime.

### 1.13 Crafting (`managers/Recipes.kt`, `listeners/RecipesListener.kt`, `commands/Craft.kt`)

Custom crafting-table + personal 2×2 grid. Crafting logic itself (`RecipesWorkspace.craft/consumeInputs/handleRemainders`) is well structured — captures the matched recipe before mutating the grid, refreshes after consuming, correctly handles remainder items (e.g. empty buckets). But `Recipes.workspaces` is a **plain `HashMap<AbstractInventory, RecipesWorkspace>`**, mutated from `PlayerSpawnEvent` (every player, every spawn), crafting-table interact, and disconnect/close — all concurrently dispatched per-chunk events. See Part 2 (HIGH).

### 1.14 Jukeboxes (`managers/Music.kt`, `listeners/MusicListener.kt`)

Registers custom `JukeboxSong`s from config with real `require()` validation at startup (positive length, non-blank name, duplicate-name detection) — fails fast on bad config, a good example other subsystems (1.9) don't follow. Internal lookup maps are plain `HashMap`s but populated once at boot before connections are accepted, then read-only — safe despite the container type.

### 1.15 Item drop/pickup physics (`managers/Items.kt`, `listeners/ItemListener.kt`)

Straightforward: throws dropped items with configurable velocity/height, delays pickup eligibility (`config.dropPickupDelayMs`), auto-despawns after `config.dropDespawnSeconds`. No shared mutable state at manager level — nothing to flag.

### 1.16 Cross-cutting utility state (`managers/Commands.kt`)

Backs `/back`, `/ignore`, `/invsee`'s ender-chest helper, and message routing. `lastLocation: HashMap<UUID, Pos>` (written on **every** entity teleport, including every elevator ride and every `/tp`/`/back`) and `ignored: HashMap<UUID, MutableSet<UUID>>` are both plain `HashMap`s — notably, `playerLastSender` in this *same file* **is** correctly wrapped in manual `synchronized{}` blocks, showing the author knows the requirement but didn't apply it consistently. `PlayerDataSerializer`/`Deserializer` call into `getIgnored`/`setIgnored` on every single player save/load (1.6), meaning this thread-safety gap sits directly on the persistence hot path, not just in incidental command state.

### 1.17 Command surface

All 20 commands extend the shared `Aechronis/utils` `Command` base class, which enforces `hasPermission()` before invoking any executor — **100% consistent usage confirmed, no bypass found**, including the two commands that are intentionally public by design (`/message`/`/msg`/`/tell`/`/whisper`/`/w`, `/reply`/`/r` — a `null` permission is documented as deliberately unrestricted, not an oversight). `hasPermission()` itself **fails closed**: any LuckPerms exception or missing-user resolves to `false` unless a `DEBUG` env var is set — a correct deny-by-default default. `/shop` demonstrates the base class's per-syntax permission overload (`vanilla.shop` to open, `vanilla.admin` to restock) rather than one blanket constructor-level permission — a real, correctly-used feature, not just boilerplate.

Commands: `/back`, `/broadcast`, `/clear`, `/convert`, `/craft`, `/ec`, `/fly`, `/gamemode` (+ `/gmc`/`/gms`/`/gmsp`/`/gma` aliases sharing one permission node), `/give`, `/ignore`, `/invsee`, `/kill` (self only), `/list`, `/message` family, `/music`, `/reply` family, `/shop`, `/teleport`/`/tp`, `/whitelist`. Validation gaps found: `/fly <speed>` has no min/max clamp (contrast with `/give`'s properly `.min(1).max(2304)`-bounded amount argument); `/teleport`'s player-to-player and player-to-coords syntaxes silently no-op with no feedback if the target isn't found; `/whitelist add|remove` accepts any string with no Minecraft username-format check; `/broadcast` has no message-length cap. None of these are permission bypasses — all are already gated correctly — just missing input validation, all low severity.

## Part 2 — Confirmed bugs & design flaws, by severity

### CRITICAL

- **Barrel-break item duplication via un-closed viewer GUI.** `listeners/StorageListener.kt::onBreak`. Breaking a barrel drops its contents as world item entities and calls `Storage.remove(key)`, but never checks `inventory.viewers` or force-closes anyone currently looking at it — unlike `Mannequin.despawn()` (1.11), which does exactly this correctly two files away in the same codebase. If Player A has the barrel's GUI open when Player B breaks it, A can still click the items out of the still-open inventory while B collects the dropped copies — a clean, repeatable two-account (or two-player-collusion) duplication exploit. Trivially discoverable at 200-player scale.
- **KillShop purchase check-then-act race — point double-spend.** `listeners/ShopListener.kt::onPreClick` + `managers/KillShop.kt`. Cooldown-check → balance-check → grant-item → deduct-balance is not wrapped in any per-player lock or atomic compare-and-swap on the points NBT tag. Two near-simultaneous click events for the same player (double-click, autoclicker, or two packets landing on different worker threads under Minestom's per-chunk parallel dispatch) can both read the same stale balance, both pass the check, both receive the item, and the loser's deduction overwrites the winner's — net effect: two items granted, only one deduction applied. Compounded by the `getOrPut` non-atomicity issue below on the same cooldown map.
- **Concurrent shutdown-save vs. in-flight disconnect-save can corrupt a player's `.dat` file.** `managers/PlayerData.kt` (`saveAll()` vs. the `PlayerDisconnectEvent` handler, both calling `savePlayer`, which does an unlocked truncate-and-write with no temp-file+rename). On server shutdown, Minestom's own teardown disconnects all online players, firing `PlayerDisconnectEvent` for each on normal event threads **at the same time** the shutdown hook's `saveAll()` is iterating the same players on its own thread — two unlocked writers to the same path can interleave/truncate the file. `loadPlayer` has no try/catch around the NBT read, so a corrupt file throws unhandled on next spawn, silently dropping that player's entire restore — and because `tracked.add()` happens *before* the load call, the player stays tracked and the next save cycle overwrites the still-recoverable corrupt backup with a fresh default-state save, turning transient corruption into permanent loss. A routine restart with 200 concurrently-connected players is exactly the scenario most likely to trigger this for many players at once.
- **`Commands.kt`'s plain `HashMap`s sit directly on the persistence hot path.** `ignored`/`lastLocation` (both plain `HashMap`, see 1.16) are read/written by `PlayerDataSerializer`/`Deserializer` on **every single player save and load** — i.e. every disconnect, every shutdown save, every first-spawn load. Concurrent disconnects/spawns (routine at 200-player scale, guaranteed during any mass-reconnect after a restart) racing on a plain `HashMap.put`/`getOrPut` is the textbook Java concurrent-resize corruption/infinite-loop hazard, and here it's exercised on the exact code path responsible for players' persisted data, not just incidental in-memory gameplay state.

### HIGH

- **`FallDamageListener`'s peak-height tracker is never reset on teleport.** Only reset on landing/water/creative-spectator/vehicle-entry. Any downward teleport of an airborne player — an elevator ride, `/tp`, `/back`, or a `nodes` home/warp/territory-spawn teleport — leaves a stale pre-teleport peak height in the map, producing potentially massive/lethal false fall damage on the player's next ordinary landing.
- **`VanillaConfig.blockDrops` is missing almost every real ore→resource conversion.** Iron/Gold/Diamond/Emerald/Redstone/Lapis/Coal/Quartz/Copper ore all fall back to dropping the ore block itself instead of the correct raw resource — a much bigger correctness gap than "no probability weighting," and directly relevant to the ore-based mining economy design in [RESEARCH.md §11](RESEARCH.md).
- **Whitelist file writes are unsynchronized against each other.** `managers/Whitelist.kt::save()` truncates and rewrites the whole file with no lock; concurrent `add`/`remove` calls (two admins, or rapid double-invocation) can interleave writes into invalid JSON. `load()` also has no try/catch around the parse, so a resulting malformed file can throw at startup and prevent the whitelist from loading at all, rather than degrading gracefully.
- **Legacy-barrel migration blocks a live event thread on synchronous disk I/O.** `managers/Storage.kt::persistAndArchiveMigration` calls `instance.saveChunkToStorage(chunk).join()` synchronously from inside the `PlayerBlockInteractEvent` handler — the first player to open any barrel still on the old sidecar-file format stalls their own interaction thread on a real, blocking chunk write. At scale (many legacy barrels touched right after an upgrade, or simultaneous access across 200 players), this produces exactly the kind of tick-thread stall Minestom's per-chunk parallel design is meant to avoid.
- **`Recipes.workspaces` is a plain `HashMap` mutated from concurrent per-player spawn/interact/disconnect events.** Same bug class as the already-known `Elevator.columns` issue, but with a higher real-world trigger probability: a post-restart reconnect burst hits `PlayerSpawnEvent` for many players near-simultaneously.
- **`Mannequin.inventories`/`corpses` are plain `HashMap`s mutated from concurrent death/interact/inventory events.** Same bug class; a lost `put()` during simultaneous deaths orphans a corpse whose armor-sync and instant-despawn-on-loot silently break (though the scheduled timeout still eventually removes it, bounding the leak).
- **No autosave / crash durability for `PlayerData` and `Storage`.** Saves only happen at disconnect (per-player) and graceful JVM shutdown (whole-server) — no periodic snapshot exists anywhere. A `kill -9`, container OOM-kill, or hard crash loses every online player's progress since their last disconnect (potentially hours) and every barrel mutation since the last graceful shutdown.

### MEDIUM

- **Kotlin's `getOrPut` is not atomic even on a `ConcurrentHashMap`.** Confirmed at two call sites: `ShopListener.onPreClick`'s `KillShop.playerCooldowns.getOrPut(...)` and `SaplingsListener.onInteract`'s `Saplings.saplings.getOrPut(...)` — `getOrPut` is a plain get-then-conditional-put, not `computeIfAbsent`, so it provides no atomicity guarantee regardless of the underlying map type. For saplings, racing bone-meal uses can silently discard one increment. For KillShop, this compounds the CRITICAL point-dupe above.
- **`Elevator` column cache goes stale on non-player-driven block changes.** Explosions, external world edits, or anything outside `PlayerBlockPlaceEvent`/`BreakEvent` never update the cached iron-column `TreeSet`. A player can be teleported to a cached level whose iron floor was destroyed by an explosion, since only the two blocks *above* the target are re-verified as air — landing them floating with no floor underneath.
- **Three managers use plain non-thread-safe collections instead of `ConcurrentHashMap`** (systemic pattern, consistent with `nodes`/`combat`): `Blocks.stonecutters` (`MutableSet<Inventory>`), `Elevator.columns` (nested nested `HashMap`), plus the newly-confirmed `Recipes.workspaces`, `Mannequin.inventories`/`corpses`, and `Commands.lastLocation`/`ignored` — contrasted against the many managers in the same repo that correctly use `ConcurrentHashMap` (`Combat`, `EnvironmentalDamage`, `FallDamageListener`, `Food`, `Crops`, `Saplings`, `Storage`, `KillShop`).
- **`VanillaConfig` has zero validation.** A bare data class with no `require()`/sanity checks on any field — negative heal amounts, zero/negative growth timers, etc. silently do whatever the downstream arithmetic implies rather than failing fast at boot. No hot-reload capability exists either, since config is a `lateinit var` assigned once with no backing file to reload from in the first place.
- **Tool durability is entirely unimplemented.** No decrement on use, no Unbreaking check, no breakage at zero anywhere in the repo.
- **A "global scheduler thread mutates per-instance state" pattern recurs** across `Crops.growthTick`, `Saplings.growthTick`, `EnvironmentalDamage.tick`, `Food.tick`, `TreeFeller.fell`'s block-clearing task, and (newly confirmed 2026-07-30) `managers/Combat.kt`'s `tick()` — flagged as needing reconciliation against whatever Minestom-threading conclusion applies to the equivalent pattern already flagged in `nodes`/`combat`. Per `research-todo/01-concurrency-model.md`'s now-confirmed finding (global scheduler runs on a separate thread pool, not the tick thread), `Combat.tick()`'s direct `player.showBossBar`/`hideBossBar`/`sendMessage` calls are a real instance of this bug class, not just a theoretical risk — same fix applies here as wherever the project-wide policy from `01-concurrency-model.md` lands.
- **`FallDamageListener` lacks per-instance/dimension scoping**, has no ladder/vine exclusion, and no Slow Falling/Feather Falling/elytra accounting — inconsistent with `EnvironmentalDamage.kt`'s correct potion-effect checks for fire/drowning in the same codebase.

### LOW

- **Crops growth is a flat global map scan every tick** with no per-instance/chunk partitioning or unloaded-chunk skip — a real scaling concern for large farms, not a correctness bug.
- **`Combat.tick()` does an O(n) linear scan of all online players per tagged player every second**, instead of an O(1) lookup.
- **Elevator's instance-keyed `columns` map is never pruned** when an instance unloads — unbounded memory growth over long uptime with many instances/worlds.
- **Mannequin creation has no rate limit or cap.** Any repeated death (fall/lava/drowning — none combat-gated) spawns a new entity + inventory; a scripted/AFK-suicide loop can transiently outpace the despawn timer. Bounded (each self-clears eventually) but a real low-effort resource-exhaustion vector at scale.
- **Input-validation gaps across the command surface**: `/fly <speed>` has no min/max clamp; `/teleport`'s player-target syntaxes silently no-op with no feedback on a missing target; `/whitelist add|remove` accepts any string with no username-format check; `/broadcast` has no message-length cap. None are permission bypasses — every command is still correctly gated — just missing input validation.
- **Whitelist is username-string based, not UUID-based, for offline-added entries** — a name change or account swap can bypass an entry that was added while the target wasn't online.
- **`PlayerData.kt` shadows its own `path` parameter** with a local `val path: Path = path.resolve(...)` in two places — a readability/maintenance risk only, not functional.
- **`Storage.register()`'s two-map update isn't atomic** (`barrels.put` then `inventoryToKey[...] =` as separate `ConcurrentHashMap` ops) — low severity since its only apparent caller is test/programmatic code, not a hot event path.
- **Informational**: no generic block-placement permission gate exists anywhere in `vanilla` (only `CropsPlantListener` self-validates farmland adjacency) — placement protection is entirely `nodes`' responsibility, matching the established pattern already confirmed for other systems.
- **Informational**: XP, beds/sleeping, and mob AI are entirely absent from `vanilla` (confirmed via full-tree review and keyword search).
- **Informational**: `PlayerData.kt` only restores health on first spawn, with no reconciliation against max-health attribute modifiers `combat`/`nodes` might apply — worth a cross-check against those libraries.
- **Informational, cross-shard risk (unconfirmed, worth verifying)**: `VanillaConfig.path` and its sub-paths are plain relative strings with no OS-level file lock, PID file, or single-writer assertion. If two shard processes are ever configured with the same `playerdata`/`whitelist` path (plausible if the intent is "player data follows a player between shards," per [RESEARCH.md §7a](RESEARCH.md)'s Redis/Mongo scoping decision), they'd have zero cross-process write coordination — the same class of race as the CRITICAL shutdown/disconnect-save bug above, just across processes instead of threads. Not confirmed as an actual current risk since `nodes`/`combat`'s config-construction code wasn't visible to this audit, but worth checking explicitly before `world-server` and any second shard share a data directory.

## Part 3 — Priority order if hardening this before launch

1. **Fix the barrel-break duplication exploit** (close viewers before/while dropping contents, mirroring `Mannequin.despawn()`) — trivially discoverable, direct economy impact.
2. **Fix the KillShop purchase race** (atomic compare-and-swap or per-player lock around the whole check-deduct-grant sequence; switch `getOrPut` to `computeIfAbsent` on the cooldown map) — direct economy/currency integrity impact.
3. **Fix the `PlayerData` shutdown/disconnect-save race** (guard `savePlayer` with a per-player lock or write-to-temp-then-atomic-rename; make `loadPlayer` fail safely instead of silently resetting state on a parse error) — data-loss risk on every routine restart at scale.
4. **Convert `Commands.lastLocation`/`ignored`, `Recipes.workspaces`, `Mannequin.inventories`/`corpses`, `Elevator.columns`, `Blocks.stonecutters` to `ConcurrentHashMap`/thread-safe equivalents** — same fix pattern across five call sites, closes the most reachable concurrency bugs cheaply.
5. **Fill in the missing ore→resource block-drop table** — directly blocks the mining-economy design in [RESEARCH.md §11](RESEARCH.md) from working correctly as-is.
6. **Fix `FallDamageListener`'s teleport reset gap** — any teleport system already planned (elevators, `nodes` warps/homes) will otherwise intermittently deal lethal false fall damage.
7. **Add an autosave interval for `PlayerData`/`Storage`**, independent of disconnect/shutdown-only saves — bounds the crash-durability gap.
8. **Add `VanillaConfig` validation** (`require()` guards on numeric fields) — cheap insurance against a config typo silently misbehaving at runtime.
9. **Lower priority**: tool durability implementation, Whitelist file-write locking + UUID-based entries, Elevator stale-cache-on-explosion fix, command input-validation gaps (`/fly`, `/teleport`, `/whitelist`, `/broadcast`), Mannequin creation rate cap.
